What shipped

Observability without provider lock-in.

The same durable event model records OpenRappter behavior whether a run uses one provider, crosses a failover boundary, invokes tools, or moves through an agent lifecycle.

🧭

Provider-neutral traces

Assistant, provider, tool, agent, and context lifecycle events share one local record, including provider failover decisions.

🔢

Trace-local sequence

Every trace carries its own ordered sequence, so forensic reconstruction does not depend on wall-clock luck or provider-specific logs.

💾

Durable continuity

SQLite WAL preserves the record across process restarts, keeping the story available after the process that created it is gone.

🧾

Integrity you can verify

SHA-256 integrity turns exported evidence into something that can be checked, not merely trusted.

📦

Atomic portability

Import and export are atomic, with a versioned flight-export envelope for moving a trace without creating a half-written record.

🐍

Python parity

The Flight Recorder is implemented in both TypeScript and Python, preserving the project’s interchangeable-runtime promise.

Privacy

Useful evidence. Deliberate exposure.

Flight Recorder is local-first and conservative by default. The event structure is recorded; raw IO is off by default.

Default

Raw IO stays off

Inputs and outputs are not captured unless the operator explicitly opts in.

When opted in

Redaction is recursive

Secret and path redaction walks nested data rather than protecting only top-level fields.

Scoped identity

Sessions and paths are hashed

Exports preserve correlation without publishing channel handles or absolute workspace paths.

Local storage

Private file modes

The default directory is 0700; the database, WAL/SHM sidecars, and atomic exports are 0600.

Operate it

Four CLI verbs. One inspectable record.

Check health, inspect events, carry evidence out, or deliberately clear local history.

$ openrappter flight status

Inspect recorder state and local continuity.

$ openrappter flight events

Read the ordered events behind recent traces.

$ openrappter flight export

Create an integrity-checked portable export.

$ openrappter flight clear

Explicitly remove the local recorder history.

Explicit limitation

One process boundary is not yet bridged.

Copilot CLI child MCP cross-process trace correlation remains an explicit limitation. The recorder does not pretend that child-process evidence is correlated when that propagation boundary has not been completed.

A truthful gap is better than a fictional trace.

Try the recorder

10 copy-paste prompts for evidence-led agents.

Each prompt asks OpenRappter to reason from its local Flight Recorder instead of guessing from the final output.

1. Forensic trace reconstruction

Use the Flight Recorder to reconstruct the most recent failed run as an ordered forensic timeline. Identify the first anomalous event, every downstream consequence, the provider/tool/agent boundaries involved, and the smallest evidence-supported root cause. Separate recorded fact from inference.

2. Provider comparison

Compare recent traces across providers. Show differences in lifecycle shape, failover decisions, tool usage, latency signals available in the events, and final outcomes. Do not rank a provider unless the local evidence supports the conclusion.

3. Privacy audit

Audit my Flight Recorder privacy posture. Confirm whether raw IO capture is enabled, inspect exported nested fields for secret and path redaction, verify absolute workspace paths are hashed, and report any value that could identify a person, credential, or local filesystem location.

4. Evidence replay

Replay the evidence from this exported flight trace as a human-readable narrative. Preserve trace-local sequence, mark assistant/provider/tool/agent/context transitions, verify SHA-256 integrity first, and flag any gap where the export cannot prove what happened.

5. Failed-agent diagnosis

Find the latest agent lifecycle that ended in failure. Trace its parent context, tool calls, provider decisions, and assistant response. Propose a fix only after citing the exact event sequence that supports it, then list the regression trace we should expect after the fix.

6. Context-budget investigation

Investigate whether context growth contributed to recent failures or provider failover. Compare context lifecycle events across successful and failed traces, identify where the working set expanded, and recommend the smallest safe compaction point without claiming token data the recorder did not capture.

7. Failover decision review

Review every provider failover decision in the latest trace. Explain the triggering evidence, the selected fallback, and the resulting outcome. Highlight any failover that was unnecessary, late, or impossible to validate from the recorded events.

8. Restart continuity proof

Prove whether Flight Recorder continuity survived the last process restart. Use trace-local sequence and persisted SQLite history to show the final event before shutdown and the first event after startup. Report discontinuities without filling them in.

9. Tool behavior audit

Audit tool lifecycle events across the last ten traces. Group repeated failures, orphaned starts, slow completions, and provider-specific patterns. Produce a prioritized remediation list where every item links back to recorded evidence.

10. Export handoff packet

Prepare a privacy-safe incident handoff from this Flight Recorder export. Verify the export schema and SHA-256 integrity, summarize the trace, include the minimum relevant event sequence, confirm recursive redaction, and state the Copilot CLI child MCP cross-process correlation limitation.
