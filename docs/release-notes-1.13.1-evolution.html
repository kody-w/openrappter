v1.13.1 - source release notes - 2026-09-07

Keep the conversation.
Keep what you remembered.

This patch focuses on the everyday path through OpenRappter Bar: signing in, continuing a conversation, reviewing a requested action, and retaining acknowledged memories. It repairs existing behavior rather than introducing another application or a separate account system.

These notes describe the source version, not proof of binary publication. The Bar releases page lists available downloads. A new installer is published only after its exact candidate bytes have completed the required promotion and signing gates.

Replies belong to their conversation

The Bar now tracks the session and run that own each response. A late reply cannot repopulate New Chat or stop a newer generation. Replies completed off-screen remain in their original local cache, while delayed history loads no longer replace a newly selected conversation or hide a submitted message. Duplicate final events produce one committed response.

First messages receive a real session identity before they are saved. Existing empty-key cache entries are reconciled: duplicate accepted messages are removed, but previously unsent text is retained in a recovered conversation. Session metadata follows the gateway's actual identifiers and timestamps.

One sign-in flow and one approval queue

First launch uses the same device-code authentication service as Settings and chat recovery. It requests a real code, handles expiration and cancellation, and does not declare completion before gateway readiness and authentication have finished. When Desktop owns the gateway, the Bar uses that authority instead of writing a competing local credential.

Checking an older installation validates its saved identity without silently overwriting divergent Keychain and environment copies. Managed CLI and Bar environment edits coordinate through a shared lock and change only their own keys. Failed credential updates do not restore old snapshots over newer settings.

Chat and Settings share the same pending approval state. Both compact and full chat layouts display the requested command and its reason. Refreshes preserve newly arrived requests without resurrecting unchanged expired ones; failures remain visible rather than looking like a successful decision.

Acknowledged memory survives concurrent writers

TypeScript and Python memory mutations hold one SQLite transaction lock across reading, changing, and replacing the JSON store. Private staged writes, file flushing, and atomic replacement prevent partial snapshots. Identifier collisions and malformed existing data fail explicitly instead of overwriting a fact or treating corruption as an empty database.

Upgrade and restart all writers together so every process participates in the lock protocol. Both runtimes must use the same memory file. These guarantees target local filesystems; they are not a certification of network storage or physical power-loss behavior. Windows file flushing does not promise POSIX directory-sync semantics.

Verified setup without security workarounds

The first-launch downloader accepts release metadata sealed into the Developer-ID-signed Bar. It verifies the selected Node archive and executable before running the sealed helper. The helper checks the frozen nightly, alpha, canary, and beta receipt chain and the exact runtime payload. Missing approvals or altered bytes stop setup; there is no fallback to a floating package version or downloaded main-branch script.

Setup stages files privately, preserves custom runtime selections, and checks Desktop ownership before activation. The Bar chooses the matching verified Node executable for its managed gateway and child processes. Release packaging must provide the architecture-specific payloads and sealed metadata before signing; it cannot add them to an already-promoted DMG. Users should not disable Gatekeeper or remove quarantine attributes.

Release evidence stays executable

The release path retains npm test, pytest, native Swift tests, builds, lint, dependency audits, mutation tests, and cold-start CLI smoke. New regressions cover concurrent memory processes, delayed replies, shared approval events, credential ownership, and interrupted setup. SHA-256 checks bind candidate files to the promoted artifact.

Developer ID signing, Apple notarization, stapling, and Gatekeeper assessment occur before the final candidate is promoted. Publication reuses those bytes instead of rebuilding after beta. Signing-account health alone is not evidence that a new DMG has shipped.
